- (idea by coach) HMW bảo vệ trang /admin/orders và API chuyển trạng thái mà không cần dịch vụ auth ngoài? → Dùng mật khẩu quản trị từ biến môi trường (ADMIN_PASSCODE) + cookie HttpOnly ký HMAC-SHA256.
- (idea by coach) HMW kiểm soát bảo mật nhất quán cho mọi route /admin/*? → Dùng src/proxy.ts (chuẩn Next.js 16 thay middleware) kết hợp kiểm tra lại quyền trực tiếp trong API route handler.
- (idea by coach) HMW giữ tồn kho tĩnh trong src/data/products.ts không bị vỡ mà vẫn trừ/hoàn kho được? → Lưu số tồn kho thực tế trong storage/inventory.json (khởi tạo tự động từ products.ts khi chưa có) và cho catalog đọc tồn kho hiện tại từ inventory-repository.
- (idea by coach) HMW tránh phá vỡ đơn hàng cũ trong storage/orders.json khi thêm statusHistory? → Đặt statusHistory là optional trên kiểu Order và tự suy ra mốc khởi tạo từ createdAt/status khi hiển thị đơn cũ.
- (idea by coach) HMW đảm bảo quy tắc chuyển trạng thái không bao giờ sai dù gọi từ UI hay API trực tiếp? → Tách máy trạng thái thành hàm thuần canTransition(from, to, actor) và getAllowedTransitions() trong src/features/orders/order-state-machine.ts kèm unit test toàn bộ ma trận 5x5.
- (idea by coach) HMW ngăn chặn xung đột khi 2 nhân viên bấm cập nhật cùng 1 đơn? → Gửi kèm trạng thái kỳ vọng (expectedStatus) hoặc kiểm tra chuyển đổi hợp lệ ở server; trả 409 Conflict nếu đơn đã đổi trạng thái trước đó.
- (idea by coach) HMW tránh mất đơn khi 2 khách đặt cùng lúc trên file JSON? → Dùng hàng đợi tuần tự (in-process write lock/mutex) kết hợp tên file tạm duy nhất (randomUUID) trước khi rename nguyên tử.
- (idea by coach) HMW giúp khách hàng dễ phân biệt đơn bị hủy bởi khách hay bởi cửa hàng? → Ghi rõ actor ('customer' | 'staff') trong statusHistory và hiển thị nhãn tương ứng trên timeline.
- (idea by coach) HMW cho phép test tự động chạy nhanh mà không chạm file thật? → Thiết kế InventoryRepository có cả bản JSON file và bản createInMemoryInventoryRepository() giống OrderRepository.
- (idea by coach) HMW giữ quy tắc khách hàng hủy đơn cũ (PATCH /api/orders/:id { status: 'cancelled' }) hoạt động không breaking? → Giữ nguyên endpoint khách hủy đơn pending; tách hoặc mở rộng endpoint riêng cho nhân viên (ví dụ POST/PATCH /api/admin/orders/:id/status) có xác thực admin.
- (idea by coach) HMW giúp nhân viên thao tác nhanh trên màn hình nhỏ/tablet tại kho? → Layout responsive dạng thẻ trên mobile và bảng trên desktop, nút bấm đủ lớn (>= 40px).
- (technique) started Reverse Brainstorming (creative) — tìm mọi cách để tính năng thất bại nhằm biến thành yêu cầu phòng thủ
- (idea by coach) [Thất bại #1: Bán vượt tồn kho (Overselling)] 2 khách đặt cùng lúc sản phẩm chỉ còn 1 cái → Yêu cầu: kiểm tra và trừ kho phải nằm trong cùng vùng khóa tuần tự (atomic reservation) trước khi lưu đơn.
- (idea by coach) [Thất bại #2: Nhân viên/kẻ xấu nhảy cóc hoặc đảo ngược trạng thái] Gọi API chuyển thẳng pending → delivered hoặc delivered → cancelled để hoàn kho khống → Yêu cầu: máy trạng thái chặn tuyệt đối nhảy bước, đi lùi và hủy đơn đã giao (trả 409/422).
- (idea by coach) [Thất bại #3: Khách tự gọi API admin để xác nhận/giao đơn của mình] Quên kiểm tra cookie HMAC ở API route, chỉ chặn ở UI → Yêu cầu: mọi route /api/admin/* bắt buộc verify session phía server (401 Unauthorized), không bao giờ chỉ bảo vệ bằng ẩn UI.
- (idea by coach) [Thất bại #4: Mất dữ liệu đơn hàng khi ghi đồng thời] order-repository.ts hiện dùng chung 1 file orders.json.tmp → Yêu cầu: sửa writeAll dùng mutex + file tạm duy nhất theo UUID.
- (idea by coach) [Thất bại #5: Hoàn kho 2 lần cho cùng 1 đơn hủy] Bấm hủy đúp hoặc retry request gây cộng tồn kho 2 lần → Yêu cầu: chỉ hoàn kho khi trạng thái trước đó chưa phải cancelled và thực hiện idempotent trong lock.
- (idea by coach) [Thất bại #6: Đơn hàng cũ bị crash trang chi tiết] Đơn trong storage/orders.json từ trước chưa có statusHistory → Yêu cầu: tương thích ngược 100%, fallback timeline từ createdAt/updatedAt/status.
- (idea by coach) [Thất bại #7: Khách hàng tự hủy đơn khi hàng đã giao cho shipper] Khách vẫn thấy nút hủy sau khi nhân viên đã chuyển sang confirmed/shipping → Yêu cầu: giữ chặt quy tắc khách chỉ hủy khi pending cả ở UI lẫn server.
- (idea by coach) [Thất bại #8: Lộ mật khẩu quản trị hoặc cookie giả mạo] Dùng mật khẩu hardcode hoặc cookie plaintext 'isAdmin=true' → Yêu cầu: đọc passcode từ env (có giá trị dev rõ ràng nếu chưa đặt), ký cookie bằng HMAC-SHA256 và so sánh bằng timingSafeEqual.
- (idea by coach) [Thất bại #9: Sai lệch tồn kho giữa trang sản phẩm và lúc đặt hàng] Catalog đọc products.ts tĩnh còn OrderService đọc inventory.json → Yêu cầu: tạo nguồn đọc tồn kho thống nhất để cả trang /products, /products/[slug] lẫn checkout/order-service đọc cùng số liệu.
- (idea by coach) [Thất bại #10: Mất dấu vết ai đã hủy đơn] Không ghi lý do/người thực hiện khi nhân viên hủy → Yêu cầu: mọi chuyển trạng thái đều append 1 bản ghi bất biến vào statusHistory.
- (idea by coach) [Thất bại #11: Gãy test E2E hiện có] Thay đổi luồng /orders hoặc /api/orders làm hỏng e2e/shopping-flow.spec.ts → Yêu cầu: giữ nguyên hợp đồng API phía khách và chạy toàn bộ npm run check + test:e2e.
- (decision) Hội tụ bằng MoSCoW cho MVP (Must <= 5 mục, không dùng dịch vụ ngoài):
- (decision) MUST 1: Máy trạng thái đơn hàng (pending → confirmed → shipping → delivered; cancelled có điều kiện) + lịch sử statusHistory tương thích ngược đơn cũ.
- (decision) MUST 2: Trang vận hành /admin/orders (danh sách, lọc theo trạng thái, tìm kiếm, chuyển trạng thái 1 bước, bắt buộc lý do khi nhân viên hủy).
- (decision) MUST 3: Bảo vệ truy cập admin đơn giản không dịch vụ ngoài (biến môi trường + cookie HttpOnly ký HMAC-SHA256 + xác thực ở proxy và API).
- (decision) MUST 4: Tồn kho thật lưu ở storage/inventory.json (trừ khi đặt, hoàn khi hủy, khóa tuần tự chống bán vượt tồn kho & sửa lỗi ghi đồng thời ở repository).
- (decision) MUST 5: Timeline tiến trình đơn hàng cho khách trên /orders/[id] (hiển thị 4 bước, mốc thời gian, giữ nguyên quy tắc khách chỉ hủy khi pending).
- (decision) SHOULD: Thẻ KPI nhanh đầu trang /admin/orders; cảnh báo sản phẩm sắp hết hàng (<= 5); kiểm tra xung đột trạng thái expectedStatus (409).
- (decision) COULD: Bật/tắt lọc theo phương thức thanh toán; xuất nhanh danh sách nhặt hàng; điều chỉnh tồn kho thủ công (nhập hàng) trong admin.
- (decision) WON'T (ngoài phạm vi MVP): Phân quyền nhiều vai trò phức tạp (RBAC), gửi email/SMS tự động cho khách, tích hợp đối tác vận chuyển ngoài (GHN/GHTK), cơ sở dữ liệu ngoài.

- (question) Câu hỏi mở 3: Nếu nhân viên chưa đặt biến môi trường ADMIN_PASSCODE ở local dev thì nên chặn truy cập hay dùng passcode dev mặc định có cảnh báo?
